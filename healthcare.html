Healthcare Analytics & Risk Prediction

A healthcare analytics system built on Google Cloud that connects data storage, analysis, machine learning, model infrastructure, and an application facing prediction service in one complete workflow.

Python · Google Cloud · BigQuery · Vertex AI · Cloud Run · Cloud Storage · Docker · Terraform · scikit learn

The problem

This project focused on building more than a predictive model. The goal was to create a complete healthcare analytics workflow that could store data, prepare it for analysis, generate risk predictions, and make those predictions available to another application through an API.

The system analyzes healthcare information to predict patient health risk and identify hospitals with greater Medicare cost exposure. That required thinking about the full path of the data, including where it is stored, how it is processed, where the model runs, and how a prediction can ultimately be consumed by another service.

Architecture

The architecture separates data storage, analytical processing, machine learning, model infrastructure, and prediction serving so that each part of the system has a clear responsibility.

Healthcare DataSource information used for analytics and prediction
Cloud Storage + BigQueryCloud storage, querying, and analytical data access
ML ProcessingPython, Pandas, NumPy, and scikit learn processing
Vertex AICloud model infrastructure and prediction workflow
Cloud RunContainerized REST API that exposes predictions

Terraform defines the Google Cloud infrastructure as code. This makes the environment reproducible and allows the cloud resources to be recreated from configuration instead of relying on a manually configured environment.

Data and modeling

Python was used for the machine learning workflow, with Pandas and NumPy supporting data preparation and scikit learn supporting model development. The prediction component was designed around healthcare risk and Medicare cost exposure rather than a generic classification example.

BigQuery provides a cloud based analytical layer for working with structured healthcare information, while Cloud Storage supports the broader data and model workflow. Keeping the analytical data layer separate from prediction serving makes the system easier to reason about and extend.

Cloud deployment

The application includes REST API services deployed with Cloud Run. The API creates a clean boundary between the machine learning system and applications that need a prediction. Instead of requiring another application to understand the model implementation directly, it can communicate with the prediction service through an HTTP interface.

Docker provides a consistent runtime for the service. Vertex AI is included in the model infrastructure, while Google Cloud logging supports visibility into the deployed environment. The repository also contains Kubernetes related work as part of the broader deployment stack.

Infrastructure as code

Terraform was used to describe the required cloud infrastructure in configuration files. This was important because the project was intended to represent a reproducible cloud system rather than a collection of manually created resources.

The live Google Cloud resources were intentionally taken offline after the project was completed to prevent ongoing cloud charges. The source code, Terraform configuration, deployment structure, and project documentation remain in the repository so the architecture can still be reviewed and recreated.

What I learned

The project gave me experience connecting several areas that are often taught separately. I worked with cloud data storage, analytical querying, machine learning, APIs, containers, infrastructure configuration, and deployment as pieces of one system.

The most valuable part was understanding that a useful machine learning project does not end when a model produces a prediction. Data access, reproducibility, deployment, interfaces, and infrastructure all affect whether a model can become part of a usable application.

Next steps

The system could be extended with automated continuous integration and deployment, authentication for the prediction API, richer healthcare dashboards, automated model retraining, model explanations using SHAP, additional healthcare datasets, and streaming data support.

Those additions would move the project further toward a continuously operated platform while preserving the same separation between the data layer, machine learning workflow, model infrastructure, and application services.
